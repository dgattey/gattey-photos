# Distributing Gattey Photos (macOS auto-update)

Small family install: **ad-hoc** code signing (`-`) + `com.apple.security.cs.disable-library-validation` + Sparkle 2 EdDSA. No Apple Developer Program.

- Sparkle 2 validates and installs updates via the EdDSA signature (`SUPublicEDKey` in `Info.plist` + `sparkle:edSignature` in `appcast.xml`, generated by `scripts/generate-sparkle-key.sh`).
- Ad-hoc signing (`-`) with `com.apple.security.cs.disable-library-validation` works cleanly with macOS Gatekeeper's **Privacy & Security → Open Anyway** flow (whereas untrusted self-signed X.509 certificates get killed by `syspolicyd`/`amfid` on macOS Sequoia/Tahoe when quarantined).
- One-time per Mac: **Privacy & Security → Open Anyway** after a blocked launch; Sparkle updates after that.
- Feed + zip live in `server/public/` and deploy with the Next.js app on Vercel (normal Git integration). The download page (`@dylkit/web`) and `/download/macos` are **statically generated from that commit’s `public/` at deploy time** — same source as Sparkle’s `appcast.xml`. After an app push, the site may still show the previous version until the `Release v…` commit’s Vercel deploy finishes; that is expected.

## How it works

- App checks `https://photos.gattey.com/appcast.xml` (Sparkle 2, HTTPS only).
- DylKit's `AppUpdater` runs only when `SUFeedURL` and `SUPublicEDKey` are in the built app; release-kit writes both from `DylApp.toml`.
- Push to **`main`** touching the `[release] inputs` in `DylApp.toml` → `.github/workflows/release.yml` runs `release-kit` (version, bundle, sign, appcast, check, publish), which commits `server/public/` and tags `v<version>` once. DylKit's `apple-release` skill documents each step and how to run them by hand on a Mac.
- That release commit only touches `server/public/**`, so the workflow does **not** run again (no loop). Vercel’s usual Git deploy picks up the new zip (often a second Production deploy after your code push — that is fine).

PRs into `main` work the same way: merge → one code push (maybe + one `Release v…` commit). No release branch and no manual steps.

## Pick the version bump in the PR

GitHub fills new PR bodies from `.github/pull_request_template.md`, which ends with a **Release info** section:

```md
# Release info

- [ ] Major
- [ ] Minor
- [x] Patch
```

Check exactly one box before you merge. From 1.0.16, a patch release is 1.0.17, a minor release is 1.1.0, and a major release is 2.0.0. Only boxes under the `Release info` heading count, so a checked item under `What changed?` does not change the version.

`release-kit version` reads the checkbox from the merged PR body (fetched by `ci/github/pr-body.sh`), falling back to the merge commit message, and fails if neither checks exactly one box. Rerun the workflow by hand with an explicit **release_type** in that case. The current version comes from the tags and the live `appcast.xml`.

## One-time setup

### EdDSA key

```bash
swift build
./scripts/generate-sparkle-key.sh
```

Commit `sparkle-public-key.txt`. Back up the private key (1Password, etc.):

```bash
.build/artifacts/sparkle/Sparkle/bin/generate_keys -x sparkle_private.key
```

### GitHub secrets

From the repo root:

```bash
gh auth login   # once
./scripts/export-ci-secrets.sh
```

That pushes `SPARKLE_ED_PRIVATE_KEY_BASE64` with `gh secret set` on **this** repository. Do not paste base64 into the GitHub UI by hand.

| Secret | Purpose |
|--------|---------|
| `SPARKLE_ED_PRIVATE_KEY_BASE64` | EdDSA private key for signing release archives in `appcast.xml` |

Options: `--print-only`, `--dry-run`, `--sparkle-key-file path`, `--repo owner/name`.

Leave Vercel **Production** Git deploys enabled (default). You do not need to change anything in the Vercel dashboard for this setup.

## First install (each family Mac, once)

1. Download from [photos.gattey.com](https://photos.gattey.com), unzip, drag **Gattey Photos** to Applications.
2. Try to open the app once (macOS will block it).
3. **System Settings → Privacy & Security → Open Anyway**, then open the app again.
4. **MDM-managed Macs (`DisableOverride = true`)**: Work MDM profiles (such as Kandji setting `DisableOverride = true` in `/Library/Managed Preferences/com.apple.systempolicy.managed.plist`) block **Open Anyway** from clearing `com.apple.quarantine` (`GKQuarantineResolver` fails with `Error -60005`). On those Macs, clear quarantine once in Terminal:

```bash
xattr -cr "/Applications/Gattey Photos.app"
```

After initial approval or `xattr -cr`, subsequent in-place **Sparkle** updates do not attach `com.apple.quarantine` and launch cleanly.

The release zip is ad-hoc signed with `com.apple.security.cs.disable-library-validation` (bundle-relative rpaths only, designated requirement pinned to `com.gattey.photos`) and verified by Sparkle 2 via EdDSA; macOS blocks unknown developers until you approve the app once via **Open Anyway** (or clear quarantine via `xattr -cr`).

## Notes

- Releases use `GatteyPhotos.local.entitlements` (`com.apple.security.network.client` + `com.apple.security.cs.disable-library-validation`, no `associated-domains`).
- `CFBundleVersion` is monotonic: the commit count, raised above every published `sparkle:version`.
- Only the latest zip is kept in `server/public/`.
